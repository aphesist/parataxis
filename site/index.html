the lanes

several lanes work on one coding task at once, each inside a typed contract, and their edits meet in a test-gated merge. on 37 fresh swe-bench pro tasks the governed lanes solved 36/37 and an ungated merge of the same first replies 28/37. that study ran on the cloud api; the local track has not run.

starting evidence: contraprova's contract lanes study, 2026-11-12 pre-registered, run local track: not run

the question

quaestio

on one consumer gpu, do parallel local lanes under contracts and a test-gated merge solve more tasks than an ungated merge of the same lane outputs, and how many test-passing tokens per second does that give?

the control is a shadow merge: the same lane outputs, token for token, merged with no contracts, no gate and no repair. so the gap between them is what the governance buys, and nothing else: not a better model, not more tokens.

method

a planner splits the task into lanes, each with a typed contract: the code it owns, the interfaces it provides and needs, its tests. an interface round freezes the signatures before any lane writes code. the lanes' edits meet in a test-gated merge, a failure is blamed on specific lanes, and only those lanes are repaired or escalated. every coordination failure is counted.

the engine is contraprova, pinned as a dependency: its event-sourced, hash-chained log with a single validating writer, its gates, statistics, pricing and the swe-bench pro harness. parataxis owns the lane layer, and adds symbol-level lanes: a lane owns functions, classes or methods rather than whole files, up to 8 lanes, with a scope gate that checks every changed line falls inside its spans.

pre-registration

the starting study was pre-registered: PREREG.md was written and committed before any paid request of the main run, on 2026-11-12 (contraprova commit 1ed672e), with its primary test fixed: La against La-shadow, exact mcnemar, holm m = 1, alpha 0.05. its probe had its own (PREREG-probe.md). the hashes it freezes refer to contraprova's paths, not to this repository's copy of the lane layer (provenance).

the local track is not pre-registered yet. its plan commits a pre-registration before the main run (docs/local-plan.md, step 4).

what it did not do

  • it did not fan out. the planner never chose more than 2 lanes. lanes owned whole files, and the largest lane held a median 80% of a task's code.
  • the planner was half the bill, and on a local gpu the lanes cost almost nothing.
  • what this project adds: symbol-level lanes, so a task can split into more than two. a $0 fit study on the same tasks, with exact count_tokens counts, finds that every symbol lane prompt fits 24K tokens (largest lane per task: median 10.2K, at most 17.1K), against 20 of 37 tasks with whole-file lanes. it is a token count with claude's tokenizer, not a run.
